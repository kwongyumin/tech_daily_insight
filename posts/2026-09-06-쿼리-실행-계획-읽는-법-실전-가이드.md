# 쿼리 실행 계획 읽는 법 실전 가이드

## 개요

쿼리 실행 계획(Query Execution Plan, QEP)은 데이터베이스 엔진이 SQL을 어떤 순서로, 어떤 방법으로 처리할지를 나타내는 청사진이다. 성능 문제가 발생했을 때 "인덱스를 추가했는데 왜 느리지?", "FULL TABLE SCAN이 왜 일어나지?"라는 질문의 답은 대부분 실행 계획 안에 있다.

많은 개발자들이 `EXPLAIN`을 실행해보지만, 출력 결과를 제대로 해석하지 못해 다시 막히는 경우가 많다. 이 글에서는 MySQL과 PostgreSQL을 중심으로 실행 계획을 실전에서 어떻게 읽고, 어떤 기준으로 튜닝 포인트를 찾아야 하는지를 구체적인 예제와 함께 설명한다.

---

## 핵심 개념

### 실행 계획의 구성 요소

실행 계획은 크게 두 가지 정보를 담고 있다.

1. **접근 방법(Access Method)**: 테이블 데이터를 어떻게 가져오는가 (Full Scan, Index Scan 등)
2. **조인 순서(Join Order)**: 여러 테이블을 어떤 순서로 결합하는가

### MySQL의 주요 컬럼

MySQL에서 `EXPLAIN` 실행 시 출력되는 주요 컬럼들이다.

| 컬럼 | 의미 |
|------|------|
| `type` | 접근 방식. `ALL`(풀스캔)이 가장 나쁘고, `const`가 가장 좋다 |
| `key` | 실제로 사용된 인덱스 |
| `rows` | 옵티마이저가 예측한 읽을 행 수 |
| `filtered` | rows 중에서 WHERE 조건을 통과할 비율(%) |
| `Extra` | 추가 정보. `Using filesort`, `Using temporary` 등 |

**`type` 컬럼의 성능 순서**:
```
const > eq_ref > ref > range > index > ALL
```

`ALL`이 보이면 즉시 의심해야 한다. 다만, 소규모 테이블이라면 의도적인 풀스캔이 더 빠를 수도 있다.

### PostgreSQL의 주요 노드

PostgreSQL은 트리 구조로 실행 계획을 출력하며, 각 노드는 다음 정보를 포함한다.

- **cost**: `시작비용..총비용` 형태로 표시 (단위는 임의 단위)
- **rows**: 예측 행 수
- **actual time**: 실제 수행 시간 (ms, `EXPLAIN ANALYZE` 사용 시)
- **loops**: 해당 노드가 반복 실행된 횟수

## 실전 예제

### 예제 1: MySQL — 인덱스가 있는데 왜 FULL SCAN이 일어날까?

다음과 같은 테이블과 쿼리를 가정한다.

```sql
CREATE TABLE orders (
    id BIGINT PRIMARY KEY,
    user_id BIGINT NOT NULL,
    status VARCHAR(20) NOT NULL,
    created_at DATETIME NOT NULL,
    INDEX idx_user_id (user_id),
    INDEX idx_status (status)
);

-- 문제의 쿼리
SELECT * FROM orders
WHERE status = 'COMPLETED'
  AND created_at >= '2024-01-01';
```

```sql
EXPLAIN SELECT * FROM orders
WHERE status = 'COMPLETED'
  AND created_at >= '2024-01-01';
```

출력 결과:

```
+----+-------------+--------+------+---------------+------+---------+------+---------+-------------+
| id | select_type | table  | type | possible_keys | key  | key_len | ref  | rows    | Extra       |
+----+-------------+--------+------+---------------+------+---------+------+---------+-------------+
|  1 | SIMPLE      | orders | ALL  | idx_status    | NULL | NULL    | NULL | 5000000 | Using where |
+----+-------------+--------+------+---------------+------+---------+------+---------+-------------+
```

**분석 포인트**:
- `type: ALL` → Full Table Scan 발생
- `possible_keys`에 `idx_status`가 있지만, `key`는 `NULL` → 인덱스를 알고 있지만 사용하지 않음
- `rows: 5000000` → 500만 건을 모두 스캔

**원인**: `status = 'COMPLETED'`가 전체의 80%를 차지하는 컬럼이라면, 옵티마이저는 인덱스를 타는 것보다 풀스캔이 낫다고 판단한다.

**해결**: 복합 인덱스로 선택도를 높인다.

```sql
-- created_at을 선행 컬럼으로 두어 범위 조건 활용
ALTER TABLE orders ADD INDEX idx_created_status (created_at, status);

-- 재확인
EXPLAIN SELECT * FROM orders
WHERE status = 'COMPLETED'
  AND created_at >= '2024-01-01';
```

```
+----+-------------+--------+-------+--------------------+--------------------+---------+------+--------+-----------------------+
| id | select_type | table  | type  | possible_keys      | key                | key_len | ref  | rows   | Extra                 |
+----+-------------+--------+-------+--------------------+--------------------+---------+------+--------+-----------------------+
|  1 | SIMPLE      | orders | range | idx_created_status | idx_created_status | 5       | NULL | 150000 | Using index condition |
+----+-------------+--------+-------+--------------------+--------------------+---------+------+--------+-----------------------+
```

`type: range`로 개선되고, rows도 15만으로 대폭 감소했다.

### 예제 2: PostgreSQL — EXPLAIN ANALYZE로 예측과 실제의 차이 파악

```sql
-- 실행 계획 + 실제 수행 시간 확인
EXPLAIN (ANALYZE, BUFFERS, FORMAT TEXT)
SELECT u.name, COUNT(o.id) AS order_count
FROM users u
JOIN orders o ON u.id = o.user_id
WHERE u.created_at >= '2024-01-01'
GROUP BY u.name
ORDER BY order_count DESC
LIMIT 10;
```

출력 예시:

```
Limit  (cost=45231.00..45231.02 rows=10 width=40) (actual time=1823.412..1823.415 rows=10 loops=1)
  ->  Sort  (cost=45231.00..45481.00 rows=100000 width=40) (actual time=1823.410..1823.411 rows=10 loops=1)
        Sort Key: (count(o.id)) DESC
        Sort Method: top-N heapsort  Memory: 25kB
        ->  HashAggregate  (cost=41000.00..42000.00 rows=100000 width=40) (actual time=1750.233..1810.512 rows=98342 loops=1)
              Group Key: u.name
              ->  Hash Join  (cost=8500.00..35000.00 rows=1200000 width=16) (actual time=120.344..1530.211 rows=1200000 loops=1)
                    Hash Cond: (o.user_id = u.id)
                    ->  Seq Scan on orders o  (cost=0.00..22000.00 rows=1500000 width=8) (actual time=0.021..450.332 rows=1500000 loops=1)
                    ->  Hash  (cost=7000.00..7000.00 rows=120000 width=12) (actual time=118.201..118.201 rows=98342 loops=1)
                          Buckets: 131072  Batches: 1  Memory Usage: 5423kB
                          ->  Seq Scan on users u  (cost=0.00..7000.00 rows=120000 width=12) (actual time=0.018..95.123 rows=98342 loops=1)
                                Filter: (created_at >= '2024-01-01'::date)
                                Rows Removed by Filter: 21658
Buffers: shared hit=12450 read=9823
Planning Time: 2.341 ms
Execution Time: 1823.891 ms
```

**분석 포인트**:

1. **Seq Scan on orders**: 150만 건 전체 시퀀셜 스캔 → `user_id`에 인덱스 추가 검토
2. **HashAggregate의 rows 예측 vs 실제**: 옵티마이저 예측(100,000)과 실제(98,342)가 근접 → 통계가 양호한 상태
3. **실행 시간의 병목**: `Seq Scan on orders`에서 450ms, `HashAggregate`에서 약 1.3초 → Aggregate 단계가 주 병목
4. **Buffers shared read: 9823** → 디스크에서 읽은 블록이 많음 → 캐시 효율 낮음

**개선 방향**:
```sql
-- orders 테이블에 복합 인덱스 추가
CREATE INDEX idx_orders_user_created ON orders (user_id, id);

-- users 테이블의 created_at 인덱스
CREATE INDEX idx_users_created_at ON users (created_at) INCLUDE (id, name);
```

### 예제 3: Extra 컬럼의 위험 신호 읽기 (MySQL)

```sql
EXPLAIN SELECT * FROM orders ORDER BY created_at DESC LIMIT 100;
```

```
+----+-------------+--------+------+---------------+------+---------+------+---------+----------------+
| id | select_type | table  | type | possible_keys | key  | key_len | ref  | rows    | Extra          |
+----+-------------+--------+------+---------------+------+---------+------+---------+----------------+
|  1 | SIMPLE      | orders | ALL  | NULL          | NULL | NULL    | NULL | 5000000 | Using filesort |
+----+-------------+--------+------+---------------+------+---------+------+---------+----------------+
```

**`Using filesort`**: 정렬을 위해 별도의 소트 패스가 필요함. 대용량 테이블에서 치명적이다.

```sql
-- 인덱스 추가로 filesort 제거
CREATE INDEX idx_orders_created_at ON orders (created_at);

EXPLAIN SELECT * FROM orders ORDER BY created_at DESC LIMIT 100;
```

```
+----+-------------+--------+-------+---------------------+---------------------+---------+------+------+-------+
| id | select_type | table  | type  | possible_keys       | key                 | key_len | ref  | rows | Extra |
+----+-------------+--------+-------+---------------------+---------------------+---------+------+------+-------+
|  1 | SIMPLE      | orders | index | idx_orders_created  | idx_orders_created  | 5       | NULL | 100  | NULL  |
+----+-------------+--------+-------+---------------------+---------------------+---------+------+------+-------+
```

Extra가 비어있고 `rows: 100`으로 극적으로 개선됐다.

## 주의사항 및 트레이드오프

### 1. rows는 추정치다

옵티마이저의 `rows` 예측은 통계 정보 기반이다. 통계가 오래됐거나, 데이터 분포가 편향된 경우 예측이 크게 빗나갈 수 있다.

```sql
-- MySQL: 통계 갱신
ANALYZE TABLE orders;

-- PostgreSQL: 통계 갱신
ANALYZE orders;

-- PostgreSQL: 특정 컬럼에 대해 더 세밀한 통계 수집
ALTER TABLE orders ALTER COLUMN status SET STATISTICS 500;
ANALYZE orders;
```

### 2. EXPLAIN과 EXPLAIN ANALYZE는 다르다

- `EXPLAIN`: 쿼리를 실제로 실행하지 않고 계획만 출력
- `EXPLAIN ANALYZE`: 쿼리를 실제로 실행하고 실측치를 함께 출력

**주의**: `INSERT`, `UPDATE`, `DELETE`에 `EXPLAIN ANALYZE`를 사용하면 실제로 데이터가 변경된다. 반드시 트랜잭션으로 감싸라.

```sql
BEGIN;
EXPLAIN ANALYZE DELETE FROM orders WHERE created_at < '2020-01-01';
ROLLBACK; -- 실제 삭제 방지
```

### 3. 인덱스가 많다고 좋은 것이 아니다

인덱스는 읽기 성능을 올리지만, 쓰기(INSERT/UPDATE/DELETE) 성능을 낮춘다. 특히 `orders` 같은 고빈도 쓰기 테이블에서 무분별한 인덱스는 역효과를 낼 수 있다.

```sql
-- 사용되지 않는 인덱스 찾기 (MySQL 8.0+)
SELECT object_schema, object_name, index_name
FROM performance_schema.table_io_waits_summary_by_index_usage
WHERE index_name IS NOT NULL
  AND count_star = 0
  AND object_schema = 'your_database';
```

### 4. 실행 계획은 환경에 따라 달라진다

- 데이터 양, 버퍼 풀 상태, 서버 부하에 따라 동일 쿼리도 다른 계획을 선택할 수 있다
- 개발 환경의 실행 계획이 운영 환경과 다를 수 있으므로, 운영 DB의 슬로우 쿼리 로그를 직접 확인하는 것이 중요하다

```sql
-- MySQL: 슬로우 쿼리 로그 설정
SET GLOBAL slow_query_log = 'ON';
SET GLOBAL long_query_time = 1; -- 1초 이상 걸리는 쿼리 로깅
```

### 5. 옵티마이저 힌트는 최후의 수단으로

옵티마이저가 잘못된 선택을 할 때 힌트로 강제할 수 있지만, 데이터 분포가 바뀌면 오히려 더 나빠질 수 있다.

```sql
-- MySQL: 특정 인덱스 강제 사용
SELECT * FROM orders FORCE INDEX (idx_status) WHERE status = 'PENDING';

-- PostgreSQL: seq scan 비활성화 (세션 단위)
SET enable_seqscan = OFF;
```

## 정리

실행 계획을 읽는 것은 단순히 `EXPLAIN`을 실행하고 결과를 보는 것이 아니다. 다음 체크리스트를 습관화하자.

| 체크 항목 | 확인 방법 |
|-----------|-----------|
| Full Table Scan 여부 | `type: ALL` (MySQL), `Seq Scan` (PostgreSQL) |
| 인덱스가 실제로 사용되는지 | `key` 컬럼, Index Scan 노드 |
| 예측 rows와 실제 차이 | `EXPLAIN ANALYZE`로 actual rows 비교 |
| filesort / temporary 발생 | `Extra` 컬럼 확인 |
| 조인 방식 | Nested Loop vs Hash Join vs Merge Join |
| 실제 병목 위치 | actual time이 가장 큰 노드 |

쿼리 튜닝은 실행 계획 → 인덱스 조정 → 쿼리 리팩토링 → 재측정의 사이클을 반복하는 작업이다. "느리다"는 감각이 아닌, 실행 계획이라는 데이터를 근거로 의사결정하는 습관이 진짜 시니어의 역량이다.
